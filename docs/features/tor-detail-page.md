# TOR Detail Page — Information Architecture & Content Specification

**Feature:** TOR Detail Page  
**Related Decision:** `0010 · Normalized TOR Detail Information`  
**Related Functional Requirement:** `FR-04: The system shall normalize data ingested from all sources into a single database schema` \
**Status:** Proposed  
**Last Updated:** 2026-09-27

## 1. Purpose

The TOR Detail Page provides a structured representation of a government procurement opportunity so that users can understand and initially evaluate the opportunity without manually reading the complete original TOR document. Rather than replacing the original document for formal verification, this page is only intended to reduce the need to open the original document during initial evaluation.

The page should transform the information defined in
`0010 · Normalized TOR Detail Information` into a format that is:

- Easy to scan
- Relevant to developers and potential contractors
- Structured consistently across different TORs
- Clear about the distinction between source information and GIPDP analysis
- Traceable back to the original TOR

The original TOR remains the authoritative source for procurement and
contractual information.

## 2. Page Structure

The TOR Detail Page may present the information from each TOR organized into the following order.

```text
TOR Detail Page
│
├── A. Procurement Information
│   ├── Project Identification
│   ├── Key Procurement Facts
│   ├── Project Overview
│   ├── Contractor Deliverables
│   ├── Technical Requirements
│   ├── Integration & Existing Environment
│   ├── Implementation & Operational Requirements
│   ├── Bid Eligibility & Qualifications
│   └── Contract & Commercial Conditions
│
├── B. Decision Support
│   ├── Profile Match
│   ├── Lock-Spec Analysis
│   └── Price Analysis
│
├── C. Status & Change
│   └── Amendment / Status Information
│
└── D. Verification
    └── Source & Traceability
````
*The grouping represents the role of the information and does not require all
information in each group to appear as one continuous visual block.*


## 3. Information Origin

The page contains two fundamentally different types of information.

### 3.1 Source Information

Information directly stated or extracted from the TOR.

Examples:

- Project title
- Budget
- Deadline
- Technical requirements
- Deliverables
- Eligibility requirements
- Contract conditions

Source information should be presented as information describing the
procurement itself.

### 3.2 GIPDP Analysis

Information generated by GIPDP using the TOR, user profile, or other
procurement data.

Examples:

- Profile Match
- Lock-Spec Analysis
- Price Analysis

Analysis should be visually distinguishable from source information.

The system should not present an analytical result as though it were a
statement made by the government in the original TOR.

## 4. Information Details

### 4.1 Project Identification

#### Purpose
Identify the procurement opportunity immediately when the user opens the page. \
The information should answer:

> "What procurement opportunity am I looking at?"

#### Display

- Project title
- Procuring organization
- Responsible department/unit, where available
- TOR/e-GP reference
- Procurement status
- Procurement category/scope
- Secondary language title, where available

#### Example

```text
Search / TOR-2026-001 / e-GP 123456789

Bangkok Metropolitan Administration
Digital Services Division

Development of Government Data Management Platform
ระบบพัฒนาระบบบริหารจัดการข้อมูลภาครัฐ

Software / IT
Open
```

#### Behavior
The information should remain visually prominent regardless of procurement status.
Status-specific information should be displayed separately rather than
changing the basic identity of the project.

### 4.2 Key Procurement Facts

#### Purpose
Present the most important procurement facts in a compact, highly visible
area. \
This information should allow a user to quickly determine whether the opportunity
is relevant and still actionable.

#### Display

Where available:

- Reference/budget price
- Submission deadline
- Delivery period
- Procurement method
- Warranty period
- Contract duration
- Penalty
- Posted date
- Source

#### Example

```text
REFERENCE PRICE
฿1,850,000

SUBMISSION DEADLINE
18 Aug 2026
6 days left

DELIVERY PERIOD
120 days

PROCUREMENT METHOD
e-Bidding

WARRANTY
3 years

DELAY PENALTY
0.20% of contract value per day
```

#### Behavior

If the procurement is open, the deadline may include a remaining-time
indicator. If the procurement is closed, the deadline should remain available as
historical information but should no longer be presented as an actionable
deadline.

### 4.3 Project Overview

#### Purpose
Explain the procurement at a conceptual level before the user reads detailed
requirements. \
This information should answer:
> "What is the government trying to accomplish?"

#### Display

- Project objective
- Main problem or purpose
- Overall requested solution/service
- Major project components
- High-level scope

#### Example
```text
The project aims to implement a centralized data management platform
to support the organization's existing information systems and improve
data access and management.

Major components:

• Data management platform
• Administration system
• Reporting
• API integration
```

#### Behavior
The overview should be concise and understandable without requiring detailed
technical knowledge.
Technical specifications should be presented in the Technical Requirements
section instead of making the overview excessively long.

### 4.4 Contractor Deliverables

#### Purpose
Describe what the successful contractor is expected to provide or perform.

This section should answer:

> "What would I actually have to deliver?"

#### Display

Deliverables may be grouped into:

- **System**
    - Software
    - Infrastructure
    - Platform

- **Implementation**
    - Installation
    - Configuration
    - Integration
    - Data migration
    - Deployment

- **Validation**
    - Testing
    - Acceptance testing

- **Supporting Work**
    - Documentation
    - Training
    - Maintenance
    - Technical support

#### Example

```text
SYSTEM
• Data management platform

IMPLEMENTATION
• System installation
• Configuration
• API integration
• Data migration

SUPPORTING WORK
• User training
• Technical documentation
• Maintenance
```

#### Behavior

Deliverables should describe contractor responsibilities rather than simply
repeating the names of systems mentioned in the TOR.

### 4.5 Technical Requirements

#### Purpose

Describe the technical conditions that the proposed solution must satisfy.\
This information should answer:

> "Can my technical solution satisfy this TOR?"

Technical requirements should not be represented only as technology names.
They should be grouped and displayed in meaningful categories.

#### Display
Technical Requirements may be grouped into:
- **Required Technologies:** \
  Technologies, platforms, frameworks, databases, protocols, or other named technical products/standards explicitly required by the TOR.
- **Required Capabilities:** \
  Technical capabilities required from the solution.
- **Infrastructure Specifications:** \
  Infrastructure specifications required from the solution.
- **Technical Constraints:** \
  Technical limits or measurable requirements.

#### Example

```text
Required Technologies
[Kubernetes] [VMware] [REST API] [PostgreSQL]

Required Capabilities
• High Availability
• Role-Based Access Control
• Monitoring
• Backup
• Replication
• Vulnerability Scanning

Infrastructure Specifications
CPU       ≥ 24 cores
Memory    ≥ 768 GB
Storage   ≥ 3.84 TB × 6
Network   10/25 GbE

Technical Constraints
RPO              ≤ 10 minutes
Availability     ≥ 99.9%
Response time    ≤ 2 seconds
Capacity         ≥ 1,000 users
```

#### Behavior

Important numeric requirements should retain their original values and units.
The system should not replace exact requirements with vague summaries such as
"high performance" when the TOR provides a measurable requirement.

### 4.6 Integration & Existing Environment

#### Purpose

Describe what existing systems, infrastructure, and environments the requested
solution must work with. \
This information should answer:

> "What existing environment will I have to work with?"

#### Display

Where available:

- Existing systems
- Existing software
- Existing hardware/infrastructure
- Existing databases
- Existing network
- External systems
- APIs/interfaces
- Data exchange requirements
- Data migration requirements
- Deployment environment
- Compatibility requirements

#### Example

```text
EXISTING ENVIRONMENT

• Existing hospital information system
• Existing patient database
• Existing government network

INTEGRATION

• REST API
• Healthcare data exchange API

MIGRATION

• Existing patient records must be migrated

DEPLOYMENT

• Government data center
```

#### Behavior

If no meaningful integration requirement is identified, the section may be
omitted or indicate that no specific integration requirement was identified.

### 4.7 Implementation & Operational Requirements

#### Purpose

Describe responsibilities related to deploying, operating, and maintaining
the solution. \
This information should answer:

> "What responsibilities exist beyond building or supplying the system?"

#### Display

Where available:

- Installation
- Deployment
- Configuration
- On-site work
- Training
- Testing
- Acceptance
- Documentation
- Maintenance
- Technical support
- SLA
- Response time
- Resolution time
- Business continuity

#### Example

```text
IMPLEMENTATION

• On-site installation
• System configuration
• Environment assessment
• Acceptance testing

TRAINING

• Administrator training
• User training

SUPPORT

• Technical support required
• Response within 4 hours

MAINTENANCE

• Preventive maintenance
• Software updates
```

#### Distinction from Contractor Deliverables

The two sections may contain related information.

The intended distinction is:

> Contractor Deliverables = What the contractor must provide.

> Implementation & Operational Requirements = What the contractor must do
> to deploy, operate, support, or maintain it.

### 4.8 Bid Eligibility & Qualifications

#### Purpose

Describe requirements that determine whether a potential bidder is eligible
and qualified to participate in the procurement. \
This information should answer:

> "Can my organization participate in this procurement?"

#### Display

Where available:

- Legal/company qualifications
- Registration requirements
- e-GP requirements
- Financial qualifications
- Required certifications
- Manufacturer/vendor authorization
- Previous experience
- Personnel qualifications
- Joint venture requirements
- Other bidder qualifications

#### Example

```text
COMPANY REQUIREMENTS

✓ Required government procurement registration

AUTHORIZATION

⚠ Manufacturer authorization required

EXPERIENCE

⚠ Previous experience with similar projects required

PERSONNEL

⚠ Certified network engineer required
```

#### Behavior

Eligibility requirements should be presented separately from technical
requirements.

For example:

```text
Kubernetes required
```

is a technical requirement.

Whereas:

```text
Manufacturer authorization required
```

is a bidder qualification.

### 4.9 Contract & Commercial Conditions

#### Purpose

Describe financial and contractual conditions that affect the contractor's
obligations. \
This information should answer:

> "What are the commercial and contractual conditions?"

#### Display

Where available:

- Payment terms
- Contract period
- Delivery conditions
- Warranty
- Penalties
- SLA obligations
- Acceptance conditions
- Milestones
- Evaluation method
- Other significant contractual conditions

#### Example

```text
REFERENCE PRICE
฿17,000,000

DELIVERY
120 days

PAYMENT
1 installment

WARRANTY
3 years

DELAY PENALTY
0.20% per day

EVALUATION
Price
```

#### Behavior

Information already shown in Key Procurement Facts does not need to be
duplicated in full. Key Procurement Facts should provide the quick view, while
this section can provide additional contractual detail.

### 4.10 Profile Match

#### Purpose

Compare the procurement opportunity against the user's profile and preferences. \
This information should answer:

> "How does this opportunity match my capabilities and conditions?"

#### Display

Where available:

- Overall match score
- Matching technologies/skills
- Missing technologies/skills
- Budget compatibility
- Project/scope compatibility
- Other matching factors

#### Example

```text
MATCH WITH YOU
84 / 100

✓ 3 of 5 technologies match your skills
✓ Budget is within your stated range
✓ Scope is within your team size

Missing:
✕ VMware
✕ Required certification
```

#### Behavior

The match result should be clearly identified as a personalized result. It should not be presented as a property of the TOR itself.

### 4.11 Lock-Spec Analysis

#### Purpose

Identify potentially restrictive or unusually vendor-specific requirements
by comparing relevant requirements with comparable procurement information. \
This information should answer:

> "Are there requirements that may be unusually restrictive compared with
> similar procurements?"

#### Display

Where available:

- Lock-spec risk indicator/score
- Overall interpretation
- Detected requirement
- Requirement category
- Reason for detection
- Relevant source excerpt
- Source page/section
- Comparable procurement information
- Normal/comparable range

#### Example

```text
LOCK-SPEC RISK
18 / 100

Nothing here looks unusual —
a first-time bidder has a real chance.

01  Past-work threshold

Requirement:
"ต้องมีผลงานพัฒนาเว็บไซต์ให้หน่วยงานภาครัฐ
วงเงินไม่น้อยกว่า 900,000 บาท"

NORMALLY
Comparable projects usually ask for about ฿700,000.

SOURCE
หน้า 7 · ข้อ 2.2.1
```

#### Behavior

The module should provide evidence for the detected condition rather than
presenting only a numerical score. 
The source requirement and comparison should remain visible so that users can
understand why the analysis was produced.

### 4.12 Price Analysis

#### Purpose

Provide historical context for the TOR's reference price using comparable
procurement information. \
This information should answer:

> "How does this project's reference price compare with similar projects?"

#### Display

Where available:

- Current reference price
- Historical median
- Difference from median
- Interpretation/range
- Comparable projects
- Comparable project year
- Comparable reference price

#### Example

```text
PRICE REALITY CHECK

Reference price as posted:
฿1,850,000

9% above median —
within the normal band for this kind of work.

MEDIAN
฿1,700,000

PROJECTS IT WAS MEASURED AGAINST

Health Department data portal
2025
฿1,620,000

Main BMA website refresh
2025
฿1,780,000
```

#### Behavior

The reference price itself is source information.
The comparison against historical projects is GIPDP analysis.
These should remain visually distinguishable.

### 4.13 Amendment / Status Information

#### Purpose

Present information related to the current procurement lifecycle and changes
to the TOR.

The same Detail Page structure should be used across different statuses.

Status changes should affect the information displayed or emphasized rather
than creating separate page designs.

#### 4.13.1 Open

##### Display

- Current status
- Submission deadline
- Requirements
- Eligibility
- Other actionable procurement information

##### Example

```text
OPEN

Submission deadline:
18 Aug 2026

6 days left
```

#### 4.13.2 Amended

##### Display

- Current status
- Amendment date
- Amendment summary
- Changed sections
- Previous requirement, where available
- Updated requirement, where available
- Link to detailed changes

##### Example

```text
AMENDED

This document changed on 20 Sep 2026.

Changes:
• Delivery period updated
• Technical specification changed

[See exactly what changed]
```

##### Behavior

The latest amendment should be prominently indicated so that users who
previously reviewed the TOR can recognize that the document has changed.

#### 4.13.3 Closed

##### Display

- Closed status
- Closing date, where available
- Awarded organization, where available
- Awarded amount, where available
- Other available outcome information

##### Example

```text
CLOSED

Awarded to:
Example Company

Award amount:
฿16,500,000
```

##### Behavior

The original procurement information remains available as historical
information.
Actionable elements such as active submission deadlines should no longer be
presented as current actions.

### 4.14 Source & Traceability

#### Purpose

Allow users to verify important information against the original TOR. \
This information should answer:

> "Where did this information come from?"

#### Display

Where available:

- Source document
- Source portal
- Original document URL
- Document version
- Page number
- Section number/title
- Relevant source excerpt
- Source date

#### Example

```text
RPO
≤ 10 minutes

Source:
TOR.pdf
Page 4 · Section 5.2.3
```

#### Behavior

Source references should be associated with important extracted information
where technically feasible.

The original TOR remains the authoritative source.

The Detail Page should not imply that the normalized information has replaced
the legal or contractual authority of the original document.

## 5. Relationship Between Sections

The sections should answer different questions and should not unnecessarily
duplicate information.

| Section                                    | Primary question                                  |
| ------------------------------------------ | ------------------------------------------------- |
| Project Identification                     | What procurement is this?                         |
| Key Procurement Facts                      | What are the important basic conditions?          |
| Project Overview                           | What is the project trying to accomplish?         |
| Contractor Deliverables                    | What must the contractor provide/do?              |
| Technical Requirements                     | What must the solution technically satisfy?       |
| Integration & Existing Environment         | What existing environment must it work with?      |
| Implementation & Operational Requirements  | What must the contractor do to deploy/support it? |
| Bid Eligibility & Qualifications           | Can the organization participate?                 |
| Contract & Commercial Conditions           | What are the contractual/commercial conditions?   |
| Profile Match                              | How does it match the user?                       |
| Lock-Spec Analysis                         | Are requirements potentially restrictive?         |
| Price Analysis                             | How does the price compare historically?          |
| Amendment / Status Information             | What is the current state and what changed?       |
| Source & Traceability                      | Where can the information be verified?            |

## 6. Missing Information

Not every TOR will contain every information category.

The page should not invent missing information.

If a required information item is not available in the source document, the
system should represent it as unavailable rather than generating an
unsupported value.

For example:

```text
Warranty
Not specified in the available TOR
```

rather than:

```text
Warranty
3 years
```

unless the source document supports that value.

Sections that contain no meaningful information may be omitted from the page
rather than displaying empty sections.

## 7. Acceptance Criteria

The TOR Detail Page should satisfy the following high-level criteria.

### AC-01 — Project Identification

A user can identify the procurement, organization, and current status from the
page header.

### AC-02 — Basic Procurement Evaluation

A user can identify the budget, deadline, delivery period, and other key
procurement facts without opening the original TOR.

### AC-03 — Project Understanding

A user can understand the purpose and high-level scope of the project.

### AC-04 — Contractor Responsibilities

A user can identify the major deliverables and responsibilities expected from
the contractor.

### AC-05 — Technical Evaluation

A user can identify the major technologies, capabilities, specifications, and
technical constraints required by the TOR.

### AC-06 — Environment and Integration

A user can identify relevant existing systems, infrastructure, interfaces,
and migration requirements.

### AC-07 — Implementation Requirements

A user can identify major installation, deployment, training, maintenance,
support, and SLA obligations where specified.

### AC-08 — Eligibility

A user can identify important bidder qualifications and participation
requirements where specified.

### AC-09 — Contract Conditions

A user can identify important commercial and contractual conditions.

### AC-10 — Decision Support

A user can view Profile Match, Lock-Spec Analysis, and Price Analysis where
the required information is available.

### AC-11 — Status and Amendments

A user can identify the current procurement status and, where applicable,
understand what changed in an amendment.

### AC-12 — Traceability

Important source-derived information can be traced back to the original TOR
where source information is available.

### AC-13 — No Unsupported Information

The page does not present unavailable information as though it were stated in
the source document.

### AC-14 — Source Authority

The original TOR remains identifiable as the authoritative source for
procurement requirements and contractual conditions.
